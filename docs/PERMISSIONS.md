# PROJECT HUB 권한 정책

## 1. 목적

이 문서는 조직과 프로젝트를 넘나드는 협업 환경에서 누가 어떤 데이터에 접근하고 어떤 작업을 수행할 수 있는지 정의한다. UI 표시 규칙이 아니라 서버가 강제해야 하는 보안 정책이다.

## 2. 기본 원칙

1. 기본값은 거부다.
2. 활성 계정과 활성 멤버십을 모두 만족해야 한다.
3. 모든 프로젝트 리소스는 반드시 프로젝트 범위 안에서 조회한다.
4. 역할은 권한 묶음이며 직군명과 동일하지 않다.
5. 최소 권한을 부여하고 필요 시 만료 또는 회수할 수 있어야 한다.
6. 제한 폴더의 명시적 거부는 일반 역할 허용보다 우선한다.
7. 프로젝트 관리자는 업무 데이터를 관리하지만 조직 전체 보안 설정까지 자동으로 관리하지 않는다.
8. 결재 상태와 작성자·담당자 관계 같은 리소스 조건을 역할과 함께 확인한다.
9. 중요 권한 변경과 접근 거부는 감사 가능한 형태로 기록한다.

## 3. 권한 계층

### 3.1 시스템 역할

| 역할 | 설명 |
| --- | --- |
| 플랫폼 관리자 (`PLATFORM_ADMIN`) | 플랫폼 운영과 프로젝트 지원을 위한 시스템 역할. 모든 접근과 변경은 감사 대상 |
| 일반 사용자 | 하나 이상의 조직 또는 프로젝트에 참여하는 기본 계정 |

시스템 운영자 권한을 애플리케이션의 조직 관리자 권한과 섞지 않는다.

플랫폼 관리자만 승인 대기 회원가입 조회·승인·거절, 승인 완료 계정 목록 조회, 플랫폼 역할 변경을 수행할 수 있다. 관리자 계정 화면과 집계는 회원가입 승인 이력이 있는 활성 계정만 포함하며 부트스트랩 시스템 계정은 제외한다.

### 3.2 조직 역할

| 역할 | 코드 | 설명 |
| --- | --- | --- |
| 조직 소유자 | `ORG_OWNER` | 조직의 최종 관리자. 소유권 및 조직 관리자 관리 |
| 조직 관리자 | `ORG_ADMIN` | 조직 정보, 조직 멤버와 프로젝트 생성 관리 |
| 조직 멤버 | `ORG_MEMBER` | 자신이 참여하는 프로젝트 중심으로 사용 |

### 3.3 프로젝트 역할

| 역할 | 코드 | 설명 |
| --- | --- | --- |
| 시행사 관리자 | `CLIENT_ADMIN` | 프로젝트 설정, 참여회사, 참여자와 모든 협업 그룹 관리 |
| 프로젝트 PM | `PROJECT_PM` | 프로젝트 운영, 하위 역할 참여자 초대와 모든 협업 그룹 관리 |
| 그룹 관리자 | `GROUP_ADMIN` | 그룹 생성 및 자신이 그룹 관리자로 지정된 그룹 관리 |
| 일반 참여자 | `PARTICIPANT` | 허용된 그룹에서 이슈·댓글·파일·일정 업무 수행 |
| 외부 협력사 | `EXTERNAL_PARTNER` | 자신에게 공개되거나 배정된 그룹과 리소스에서 제한된 협업 수행 |
| 읽기 전용 사용자 | `READ_ONLY` | 허용된 프로젝트·그룹 정보 읽기 |

기존 `PROJECT_ADMIN`, `PROJECT_MANAGER`, `CONTRIBUTOR`, `REVIEWER`, `VIEWER` 코드는 이전 데이터 호환을 위해 유지하며 신규 부여에는 위의 새 역할 코드를 사용한다.

### 3.4 협업 그룹 역할

| 역할 | 코드 | 설명 |
| --- | --- | --- |
| 그룹 관리자 | `GROUP_ADMIN` | 해당 그룹 정보와 그룹 참여자 권한 관리 |
| 그룹 멤버 | `MEMBER` | 해당 그룹의 일반 협업 기능 사용 |
| 읽기 전용 | `READ_ONLY` | 해당 그룹 데이터 조회만 허용 |

프로젝트의 `GROUP_ADMIN` 역할만으로 모든 비공개 그룹을 관리할 수는 없다. 각 그룹의 그룹 멤버십에서도 `GROUP_ADMIN`으로 지정되어야 한다.

시행사, 설계사, 시공사 등의 소속·직군은 프로필 메타데이터로 보존하며 프로젝트 역할을 자동 결정하지 않는다.

## 4. 권한 계산 순서

서버는 요청마다 다음 순서로 판단한다.

1. 유효한 인증 정보인지 확인한다.
2. 사용자 계정이 활성 상태인지 확인한다.
3. 요청 URL의 `projectId`와 리소스의 실제 `project_id`가 일치하는지 확인한다.
4. 활성 프로젝트 멤버십과 프로젝트 상태를 확인한다.
5. 프로젝트 역할에 해당 행위 권한이 있는지 확인한다.
6. 제한 폴더, 명시적 접근 목록, 결재 단계 등 리소스 조건을 적용한다.
7. 소유자·작성자·담당자 조건을 적용한다.
8. 허용 또는 거부 결과와 필요한 감사 이벤트를 확정한다.

클라이언트가 보낸 역할, 조직 ID, 작성자 ID는 권한 근거로 신뢰하지 않는다.

프로젝트 참여자는 소속 회사인 `organization_id`를 반드시 가지며 하나의 프로젝트에 서로 다른 여러 회사의 참여자가 함께 참여할 수 있다. 협업 그룹 멤버십은 프로젝트 멤버십을 참조하므로 다른 프로젝트의 멤버를 그룹에 직접 추가할 수 없다.

## 7. 리소스별 상세 정책

### 7.1 프로젝트 멤버

- `PROJECT_ADMIN`만 프로젝트 역할을 부여하거나 변경할 수 있다.
- `PROJECT_MANAGER`에게 초대 권한을 허용할 경우 `CONTRIBUTOR`, `REVIEWER`, `VIEWER`만 부여할 수 있다.
- 사용자는 자신의 역할을 높일 수 없다.
- 마지막 프로젝트 관리자는 스스로 나가거나 비활성화할 수 없다.
- 멤버 비활성화는 새 접근을 즉시 차단하되 기존 작성물은 삭제하지 않는다.
- 초대 토큰은 단일 사용, 만료시간, 안전한 난수와 해시 저장을 적용한다.

### 7.2 이슈와 댓글

- 그룹 이슈 피드는 먼저 프로젝트 멤버십을 확인한 뒤 URL의 `projectId`, `groupId`, 게시글의 실제 `project_id`, `group_id`를 모두 일치시킨다.
- 비공개 그룹은 해당 그룹 멤버 또는 프로젝트 PM 이상만 조회하며, 그룹 `READ_ONLY` 및 프로젝트 `READ_ONLY` 사용자는 작성할 수 없다.
- 게시글 수정·삭제(보관)는 플랫폼 관리자만 허용한다. 일반 참여자는 자신의 게시글도 수정하거나 삭제할 수 없다.
- 담당자는 같은 그룹의 활성 참여자 또는 프로젝트 PM 이상만 지정할 수 있다.
- 첨부의 내부 객체 키는 API 응답에 노출하지 않고 업로드·다운로드마다 그룹 권한을 다시 확인한다.
- WebSocket 연결 인증 후에도 그룹 룸 구독과 재동기화 요청마다 현재 프로젝트·그룹 멤버십을 검사한다.
- 권한이 없는 사용자는 실시간 룸에 참여할 수 없으며 이벤트와 알림을 수신하지 않는다.
- 모든 조회와 변경은 이슈의 `project_id`와 요청 프로젝트를 함께 검증한다.
- 참여자가 이슈를 수정할 수 있는 범위는 제목, 본문, 분류, 중요도, 담당자, 마감일과 상태이며 프로젝트 정책으로 축소할 수 있다.
- 완료된 이슈를 다시 여는 행위는 PM 이상 또는 담당자에게만 허용한다.
- 댓글이 달린 이슈의 참여자 삭제는 소프트 삭제로 처리한다.
- 댓글 수정·삭제는 본인 또는 PM 이상만 가능하며 수정 이력을 보존한다.
- 멘션은 해당 프로젝트의 활성 멤버만 지정할 수 있다.

### 7.3 파일과 폴더

- 공유 파일함 접근에는 PROJECT HUB 로그인과 사용자의 Google OAuth 승인이 모두 필요하다.
- 개인 드라이브와 공유 드라이브의 조회·생성·수정·휴지통 이동 권한은 Google Drive의 실제 사용자 권한을 기준으로 한다.
- PROJECT HUB 역할이 Google Drive에 없는 권한을 추가로 부여하지 않는다.
- 공유 드라이브 항목 요청에는 `supportsAllDrives=true`를 사용하고 드라이브별 목록 범위를 명시한다.
- 액세스 토큰은 브라우저 메모리에만 보관하며 감사 로그나 영구 저장소에 기록하지 않는다.
- 운영 환경에서 프로젝트 멤버십과 Drive 폴더 접근을 동시에 제한하려면 서버 중계 및 연결 매핑 정책을 추가해야 하며, 현재 클라이언트 직접 연동을 프로젝트 ACL의 대체로 간주하지 않는다.

### 7.4 캘린더

- 일정 목록은 프로젝트 멤버십을 먼저 확인하고, 그룹이 없는 일정과 사용자가 접근 가능한 그룹 일정만 반환한다.
- 그룹 전용 일정의 상세 조회·수정·첨부 다운로드는 매 요청마다 그룹 권한을 다시 검사한다. 직접 URL로 접근해도 권한이 없으면 리소스 존재를 노출하지 않는다.
- 일정 작성자, 프로젝트 관리자와 PM만 일정을 수정·보관할 수 있다.
- 담당자·참여자·관련 이슈는 동일 프로젝트 소속이어야 하며, 관련 이슈는 일정과 동일한 그룹이어야 한다.
- 알림 목록과 읽음 처리는 수신자 본인에게만 허용하고, 프로젝트 멤버십이 회수되면 기존 알림도 조회하지 못한다.
- 첨부파일 업로드·다운로드는 일정 접근 권한, 허용 확장자, MIME 헤더와 실제 객체 크기를 확인한다.
- 결재 마감 등 시스템 생성 일정은 원본 리소스에서만 변경하며 캘린더에서 직접 수정하지 못한다.

### 7.5 결재

- 활성 프로젝트 참여자는 순차 결재선 템플릿을 만들고 기안에 사용할 수 있다. 템플릿 수정·삭제는 작성자 또는 플랫폼 관리자만 수행한다.
- 템플릿에는 회원가입 승인이 완료된 활성 회원을 결재자로 지정할 수 있으며 서버가 저장 시 계정 승인·활성 상태를 다시 검증한다.
- 프로젝트 비참여 결재자는 자신에게 실제 배정되어 상신된 결재 문서와 본인 알림에만 접근할 수 있고, 프로젝트의 다른 문서·파일·이슈에는 접근할 수 없다.
- 작성자만 자신의 임시 저장 문서를 수정·삭제·상신할 수 있다. PM 이상은 보안 사고나 운영 지원 목적 외에 타인의 초안을 임의 수정하지 않는다.
- 결재 중 문서 내용과 결재선은 누구도 수정할 수 없다.
- 현재 활성 순번의 지정 결재자만 승인 또는 반려할 수 있다.
- 자신의 결재 단계가 아닌 사용자는 PM이나 관리자여도 대신 승인할 수 없다.
- 작성자는 첫 승인 전만 회수할 수 있다.
- 상신 시 선택한 파일 버전·객체 키·SHA-256 해시를 불변 리비전에 고정한다.
- 반려·회수된 문서는 수정 후 새 리비전으로 재상신하며 이전 자료와 처리 이력은 보존한다.
- 승인·반려 API는 중복 실행과 경합을 방지해야 한다.
- 모든 결재 작업은 행위자, 시각, 의견, 이전/이후 상태와 리비전을 감사 로그에 남긴다.

### 7.6 대시보드와 검색

- 집계 쿼리는 사용자가 접근 가능한 프로젝트 ID 집합을 먼저 적용한다.
- 제한 폴더의 파일과 접근 불가 결재 문서는 검색 결과, 개수, 최근 활동에도 노출하지 않는다.
- 비공개 그룹의 이슈·일정은 프로젝트 관리자 또는 해당 그룹 참여자의 집계와 검색에만 포함한다.
- 전체 검색은 프로젝트, 이슈, 일정, 파일, 결재 유형마다 동일한 프로젝트·그룹·폴더 권한을 다시 적용한다.
- 접근권한이 사라지면 캐시된 대시보드와 검색 결과도 즉시 무효화한다.

## 8. API 응답 정책

- 인증되지 않은 요청은 `401 Unauthorized`를 반환한다.
- 인증되었지만 행위 권한이 없는 요청은 `403 Forbidden`을 반환한다.
- 다른 프로젝트의 리소스 존재 자체를 숨겨야 하는 경우 `404 Not Found`를 반환한다.
- 목록은 권한 없는 항목을 필터링하며 부분적인 민감 필드를 임의로 포함하지 않는다.
- 권한 오류 메시지는 내부 역할 구조나 대상 사용자의 개인정보를 노출하지 않는다.

## 9. 감사 대상

최소한 다음 이벤트를 감사 로그에 남긴다.

- 로그인 성공·실패 임계치 초과, 로그아웃, 세션 폐기
- 조직 및 프로젝트 생성·수정·보관
- 멤버 초대, 초대 수락, 역할 변경, 비활성화
- 승인 완료된 Gmail 회원의 Google 공유 드라이브 편집 권한 초대
- 제한 폴더 생성과 접근 목록 변경
- 파일 업로드 완료, 다운로드, 새 버전, 이동, 삭제
- 결재 상신, 회수, 승인, 반려
- 감사 로그 조회와 내보내기
- 권한 거부 반복 및 비정상적인 다운로드 시도

감사 로그 자체의 열람도 감사 이벤트로 남긴다. 보존 기간은 운영·법무 정책 확정 후 설정한다.

## 10. 권한 테스트 기준

모든 보호 API는 최소 다음 테스트를 가져야 한다.

1. 각 허용 역할의 정상 요청
2. 각 비허용 역할의 `403` 또는 `404`
3. 비멤버의 접근 거부
4. 비활성 계정과 비활성 멤버의 접근 거부
5. URL의 프로젝트 ID와 리소스 프로젝트 ID 불일치 거부
6. 제한 폴더 상속과 명시적 거부
7. 작성자·담당자·결재자 조건의 경계 사례
8. 직접 API 호출로 UI 제한을 우회하려는 시도
9. 캐시가 권한 변경 후 이전 데이터를 반환하지 않는지 확인
10. 동시 결재·동시 역할 변경의 경합 테스트

권한 관련 테스트 실패는 릴리스 차단 사유이며 테스트를 비활성화하여 우회하지 않는다.
