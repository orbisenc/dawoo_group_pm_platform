# PROJECT HUB 운영 런북

## 1. 운영 원칙

- 운영 환경에서는 `ENABLE_DEV_AUTH=false`를 강제하고 실제 `.env`와 비밀을 저장소에 커밋하지 않는다.
- 모든 장애·배포·복구 작업은 시작 시각, 담당자, 변경 내용, 검증 결과와 종료 시각을 운영 기록에 남긴다.
- 운영 데이터 점검은 읽기 전용 쿼리를 우선하고 삭제·복구·권한 변경은 2인 확인 후 수행한다.
- 요청 ID를 사용자 문의와 로그 검색의 공통 식별자로 사용한다. 비밀번호, OAuth 토큰, 서명 URL과 파일 본문은 기록하지 않는다.

## 2. 상태와 메트릭

| 점검 | 주소 | 정상 기준 |
| --- | --- | --- |
| 생존 상태 | `GET /api/v1/health` | HTTP 200, `status=정상` |
| 준비 상태 | `GET /api/v1/health/ready` | HTTP 200, DB·Redis·S3 모두 `정상` |
| 운영 메트릭 | `GET /api/v1/operations/metrics` | `x-metrics-token` 인증 후 HTTP 200 |

메트릭 엔드포인트는 외부 공개 경로에서 차단하고 모니터링 시스템만 접근하도록 방화벽을 설정한다. `METRICS_TOKEN`은 애플리케이션 비밀 저장소에서 주입하며 분기마다 또는 노출 의심 시 즉시 교체한다.

필수 대시보드 패널:

1. 5분/1시간 요청 수와 5xx 비율
2. 핵심 API 경로별 p95 응답시간
3. PostgreSQL, Redis, S3 준비 상태
4. BullMQ 대기·실패 작업 수와 Google Drive 초대 최종 실패 수
5. 배포 버전과 최근 배포 시각

기본 경보 기준:

| 심각도 | 조건 | 초기 대응 시간 |
| --- | --- | --- |
| 긴급 | 준비 상태 3회 연속 실패, 5xx 10% 이상 5분, 데이터 손상 의심 | 10분 |
| 높음 | 5xx 2% 이상 10분, 핵심 API p95 1초 초과 10분, 큐 최종 실패 발생 | 30분 |
| 보통 | 핵심 API p95 500ms 초과 15분, 저장공간 80% 초과 | 영업시간 4시간 |

## 3. 구조화 로그

API 요청 로그는 한 줄 JSON으로 `type`, `requestId`, `method`, `path`, `statusCode`, `durationMs`를 기록한다. 오류 로그는 여기에 안전한 오류 `code`를 추가한다. 쿼리 문자열과 요청 본문은 기록하지 않는다.

조사 순서:

1. 사용자에게 오류 화면의 요청 ID와 발생 시각을 받는다.
2. 요청 ID로 API 로그를 검색한다.
3. 동일 시간대 준비 상태와 DB·Redis·S3 지표를 확인한다.
4. 권한 또는 결재 사건이면 별도 `AuditLog`와 대조한다.
5. 개인정보가 포함된 로그를 발견하면 즉시 접근을 제한하고 보안 사고 절차를 시작한다.

## 4. 일일·주간 점검

매일:

- 준비 상태와 최근 24시간 5xx·큐 실패 확인
- 마지막 백업 성공과 백업 파일 SHA-256 확인
- Google Drive 초대 실패 및 OAuth 지원 문의 확인

매주:

- `pnpm check:security` 결과 확인
- 파일 메타데이터와 객체 저장소 표본 대조
- 관리자·프로젝트 역할 변경 감사 로그 검토
- 용량과 p95 추세 검토

매월:

- `scripts/restore-rehearsal.ps1`로 격리 복구 리허설
- 비활성 계정·만료 데이터 보존정책 실행 결과 검토
- 관리자 권한과 메트릭 접근 토큰 보유자 재검토

## 5. 장애 대응

자세한 역할과 절차는 [INCIDENT_RESPONSE.md](./INCIDENT_RESPONSE.md)를 따른다. 데이터 손상 의심 시 쓰기 기능을 중지하고 백업을 보존하며, 원인이 확인되기 전 마이그레이션 재실행이나 운영 DB 직접 수정을 하지 않는다.
